# 前端 Take-Home 作业 — Apsu 首页

> 本文件是甲方原始需求 [Front-End Take-Home Assignment.pdf](Front-End%20Take-Home%20Assignment.pdf) 的**逐句中文译本**，结构、编号、条目与英文原文一一对应，不增删、不解读。
> 有歧义时以英文 PDF 原文为准。译于 2026-09-16。

**交付一个 GitHub 仓库 · 允许使用 AI 工具**

把设计稿（桌面端 + 移动端）实现为一个 React 组件库 + 一个页面。

## 1. 技术栈

- Next.js（App Router）+ React + TypeScript（strict）+ Tailwind CSS；提交 lockfile。
- 其余一切——设计 token、图片与图标处理、状态管理、路由、API 契约与数据层如何设计——由你决定。

## 2. 目录

不规定目录结构——你如何组织代码库本身就是评估的一部分。在 README 里解释你的结构。

## 3. 数据（没有 API 文档）

后端尚不存在。所有动态内容的数据形状由你设计——它们就是未来的 API 契约——并提供符合这些形状的 mock 数据，代替后端。我们会先读类型。

## 4. 必做项

**A. 整页保真。** 每个区块、桌面端 + 移动端、默认状态，在两块画板宽度（375 / 1440）下忠实于设计稿——以你在 C 项中记录的修正为前提。

**B. 响应式底线。** 从 320 到 1920 的每一个宽度下页面都保持完整：无横向溢出、导航项不换行、内容不重叠不裁切。像素级保真只在两块画板处评判；本条讲的是完整性，不是保真度。

**加分项：** 画板之间与画板之外的优雅适配是加分项——你如何做到的会在答辩时讨论。

**C. 设计缺陷修正。** 设计稿里存在真实的错误——文案错别字、有问题的 UI。凡你判断设计有错之处，修正它，并把每一处偏差记录在 README 中（改了什么、为什么）。

**D. 交互状态与动效。** 每个可交互元素都需要 hover / focus / pressed 状态与过渡动画——设计稿有规定的地方遵循设计稿，设计稿没说的地方用你自己的 UI/UX 判断（该文件没有 hover 设计；由你来设计）。一致性与克制比数量更重要。在 README 中列出你自行设计的状态。

**E. Storybook。** 每个有状态的组件，每个状态一个 story——哪些组件、哪些状态由你决定；我们会逐个走查。

## 5. README

必须包含以下内容——其余由你决定：

- 你用了哪些 AI 工具，它们写了哪些部分？（指向对应的会话日志——见 §6。）
- 偏差日志：每一处设计修正（C）与每一个自行设计的交互状态（D）——是什么、为什么。

## 6. 提交与验收

提交一个 GitHub 仓库链接。保留完整的 commit 历史——不要 squash；历史是提交物的一部分。

如果你使用了 AI 工具，会话日志是提交物的一部分：把本项目**完整、未经编辑**的会话记录（例如 Claude Code 会话转录、Cursor / ChatGPT 导出）放进仓库的 `ai-logs/` 目录下。日志可能会在答辩时被抽样讨论；使用 AI 没问题——未披露或不可复现的 AI 使用不行。

我们将运行：

```
npm install
npm run build        # 通过
npm run dev          # 对照 Figma；在 320–1920 之间调整宽度
npm run storybook    # 逐个状态走查组件
```
